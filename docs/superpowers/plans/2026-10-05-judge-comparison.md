# Judge: план реализации

> Исполнение: superpowers:executing-plans, последовательно в текущей ветке.
> Применять superpowers:test-driven-development и verification-before-completion.

**Цель:** сравнение одного оригинала и двух переводов с доказательствами,
машинными оценками 1–5 и достоверным временем автопилота.

**Архитектура:** домен определяет проверку доказательств, рубрику и время;
сервисы координируют работу; адаптеры владеют HTTP, хранением и бюджетом.
Judge получает результат платформы через API и не исправляет его.

**Стек:** Python 3.12, FastAPI, SQLite, httpx; Next.js 15, React 19, TypeScript.

**Спецификация:** [judge-comparison-design.md](../../judge-comparison-design.md).

## Ограничения

- До 18 000 знаков оригинала, без обрезки. Исторический корпус — отдельный режим.
- EN/RU. Название Judge. Kitabs.ai опционален; ручная проверка не обязательна.
- Время LLM-чата неизвестно. Время Kitabs.ai = длительность обработки +
  5 секунд за фактически применённую операцию аудита или редактуры.
- Корректор входит только в длительность. Дубли, no-op и отклонения не считаются.
- Пропуск журнала отличается от подтверждённого пустого журнала.
- Новая методика имеет отдельную версию; старые отчёты неизменны.
- Только Vercel AI Gateway; резерв перед запросом. Общий лимит серии $3,
  уже учтённые расходы сохраняются. Нет push, deploy и изменений production.
- Продолжение по текущему Git. Чужие изменения не включаются в коммиты.

## Основные риски проверки

1. Accepted без доказанного изменения текста не означает применённую правку.
2. Потеря ответа запуска не разрешает повторить оплачиваемую работу.
3. Симметричные тексты не могут получить разные оценки без основания.
4. Неоднозначная цитата не подтверждает машинную оценку.
5. Сохранённый отчёт с другими хэшами или настройками не является кэшем запуска.

## Задача 1: журнал времени и изменение бюджета

Файлы: новый `domain/processing_effort.py`; изменение
`infrastructure/budget_repository.py`; тесты `test_processing_effort.py`,
`test_budget_gateway.py`. Все Python-пути относительно
`backend/src/independent_judge/`, тесты — `tests/`.

Интерфейс: `processing_effort(record: dict) -> dict` возвращает стороны,
длительность, число операций аудита/редактора, смоделированное время и итог.
Вход: хэши scope и серверные измерения сторон; идентичность операции включает
job/chunk/stage/artifact/edit. Интервалы объединяются до суммирования.
`BudgetLedger.amend_policy(...)` атомарно меняет явно разрешённые лимиты,
проверяя ожидаемую прежнюю политику и сохраняя все расходы и резервирования.

`paired_consensus.py`, `structural_checks.py`, `application/paired_runner.py`;
изменения `application/judge_runner.py`; тест `test_paired_comparison.py`.

Интерфейсы: `paired_prompt(scope, order) -> Prompt`,
`parse_assessment(text, scope, order) -> dict`,
`reconcile_assessments(passes, scope) -> dict`,
`structural_checks(texts, boundaries=None) -> dict`.
Результат: шесть критериев, раздельные оценки сторон, точные цитаты и координаты,
устойчивость, преимущества; без общего взвешенного балла. Второй проход меняет
порядок. Неустойчивые оценки остаются видимыми с флагом, без выдуманного итога.

## Задача 3: конфигурация выбранного судьи

Файлы: `domain/evaluation.py`, `reviewed_models.py`, `infrastructure/gateway.py`,
`runtime_evaluation.py`, `operator_config.py`, отдельный конфиг Kimi и тесты.

Интерфейс JudgeConfig сохраняет точную модель, температуру, max_tokens и цены.
HTTP и CLI используют одну валидацию. Бюджетный каталог расположен явно,

## Задача 4: встроенный автопилот

Интерфейсы: порт `start`, `status`, `completed`; сервис сохраняет идентичность
запроса и платформенного задания до начала выполнения. HTTP origin и токен

но разрешает проверку уже известного job_id. Возобновление — только GET статуса.
Получение B сверяет оригинал, окончательную сборку и артефакты. Неподтверждённые
измерения времени возвращаются как неизвестные.
